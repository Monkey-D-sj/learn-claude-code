# 代码审查

## 步骤

1. 先定范围。用户指定了文件或目录就用它;没指定就跑 `bash` 看
   `git diff --stat`,再 `git diff` 看具体改动。改动为空时直接问用户要范围,
   别自己猜一个。
2. 读**完整文件**,不只看 diff。缺上下文的审查会把正常写法误判成 bug
   (比如改动行外面已经做了空值检查)。
3. 每一类都过一遍,不要只挑顺眼的看:
   - 正确性:边界条件(空输入、单元素、零、负数)、错误路径、
     资源释放(文件句柄、连接、锁)
   - 并发:共享可变状态、检查后再使用、迭代中修改集合
   - 安全:外部输入进 shell / SQL / 文件路径;凭据写进代码或打进日志
   - 可读性:命名和职责不符、嵌套超过三层、复制粘贴出来的重复逻辑
4. 每条发现必须给出 `文件:行号`,并说明**什么输入会让它出错**。
   说不出触发条件的那是口味,不是缺陷,删掉。

## 报告格式

按严重程度从高到低,每条一行:

    [严重] path/to/file.py:42 — 描述。触发:参数 x 为负数时索引越界
    [中等] path/to/file.py:88 — 描述。触发:连接失败时不会走到 close
    [轻微] path/to/file.py:12 — 描述

没发现问题就直说"未发现问题"。不要为了凑数把风格偏好写成缺陷 ——
假阳性会让整份报告失去可信度。
