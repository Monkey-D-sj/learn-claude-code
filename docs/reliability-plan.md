评估日期：2026-09-22

## 1. 结论与目标

下一阶段建议优先保证三件事：工具结果能准确表达成功或失败，任务终态与持久化结果一致，重复启动与并发操作不会破坏已有任务。完成这些修复后，再增加主动取消和中断恢复能力。

项目已经具备终端与网页入口、模型流式输出、工具调用、子 Agent、分层上下文压缩、SQLite 会话记录和用量统计。现阶段继续增加工具的收益，低于把现有执行流程做可靠。

本轮建议的交付目标：

1. Shell 返回结果包含退出码，失败不会伪装成无输出的成功。
2. 第二个服务实例不能修改第一个实例正在执行的任务。
3. 上下文保存失败时，页面明确显示保存失败，不能只显示任务完成。
4. 删除与执行使用同一把会话锁，消除检查与实际操作之间的竞态。
5. 用户可以停止任务；已发生的文件修改不会被宣称已撤销。
6. 进程中断后能展示最后可靠检查点，并明确说明哪些操作结果不确定。

## 3. 当前执行流程

```text
网页提交请求
  → 检查会话、取得会话锁
  → 读取模型上下文、创建 running 轮次
  → Agent 循环
      → 必要时压缩，并保存压缩检查点
      → 请求模型
      → 记录响应
      → 执行工具、记录结果
      → 把整批工具结果加入工作上下文
  → 在同一事务中保存最终上下文和任务终态
  → 向页面发送最终回复
  → 释放会话锁
```

需要区分三份数据：

- `turn_messages` 保存轮次中的原始消息，服务于查看历史。
- `events` 保存展示事件，服务于页面增量更新。
- `session_contexts` 保存后续请求会重新发送给模型的工作上下文。

页面能看到工具结果，并不自动意味着下次模型请求能够加载到该结果。中断恢复必须检查工作上下文，不能只检查历史消息是否存在。

## 5. 逐项修复方案

### R1：Shell 失败没有可靠的状态信号

**位置：** [tools/bash.py](../tools/bash.py) 的 `run_bash()`。

当前读取 `stdout` 和 `stderr`，拼接后返回文本，没有返回 `CompletedProcess.returncode`。没有输出时统一返回 `(no output)`。

**触发示例：** `exit 0` 与 `exit 1` 都没有输出，现有返回文本无法区分两者。安装、构建或检查命令失败时，模型可能继续基于错误前提执行。stderr 有文字也不一定表示失败，因此不能改成“有 stderr 就失败”。

**最小修复：** 保持工具 handler 返回字符串的接口，统一包含退出码、stdout 和 stderr。超时与启动失败使用明确状态。输出截断时保留状态和截断标记；不要求这一步把所有工具重构成新类型。

**验收：** 成功无输出、失败无输出、成功但有 stderr、非零退出且有 stdout、超时、进程启动失败六种情况都能区分。返回内容超长时，退出码仍可见。

**补充限制：** 当前先完整捕获输出再截断文本，400000 字符上限不是内存使用上限。超时限制运行时长，也不保证内存有界。需要处理大量输出时，应另做流式读取与落盘，不与退出码修复捆绑。

#### 实施记录（2026-09-22）

已按上文“最小修复”落地：`tools/bash.py` 的返回文本改成一行的状态头加 stdout / stderr 两段，`tests/test_bash.py` 新增 13 项测试。工具接口没变，仍返回字符串，只动了 Shell 这一处。

实际返回形态：

```text
status: exit 0            status: exit 2            status: timeout after 120s (killed)
(no output)               stdout: o                 stdout: started
                          stderr: e
status: failed to start ([WinError 2] ...)
```

三处与方案文字的偏差，都是写的时候才暴露的约束：

1. **段标跟在首行上（`stdout: o`），不独占一行。** 页面折叠着的工具结果拿 `headline()` 当摘要，而那是**头两行**（ui/index.html）。段标独占一行的话每格摘要都变成 `status: exit 1 / stderr:`，报错本身反而看不见了。
2. **状态头不参与截断。** 400000 那一刀只切正文，状态头必须在，否则又回到“超长就看不出成败”。截断标注仍在尾部——落盘预览是头 2000 + 尾 300，两头都看得见。
3. **超时状态里不写退出码。** 超时是“没跑完”，副作用可能只做了一半，跟“执行了但失败”不是一回事；起不来同理（命令根本没执行过，重试有意义）。两者都借独立状态表达，不编造一个退出码。超时带上卡住前那半截输出。

验收对照（`uv run pytest tests/test_bash.py`，13 项全过；全套 211 项全过）：

| 方案要求 | 用例 |
| --- | --- |
| 成功无输出 | `test_成功无输出` |
| 失败无输出 | `test_失败无输出` |
| 成功但有 stderr | `test_成功但有stderr` |
| 非零退出且有 stdout | `test_非零退出但有stdout` |
| 超时 | `test_超时是独立状态不是退出码` |
| 进程启动失败 | `test_起不来跟失败分开` |
| 超长时退出码仍可见 | `test_超长时状态仍可见_截断标在尾部` |
| 六种结局两两可区分 | `test_六种结局两两不同`（逐条比对，不是抽样） |

实施中发现的两件事，都不属于 R1 的交付范围，留在原处：

- **超时到返回之间有一段不受控的等待。** 触发：`TIMEOUT_SECONDS=0.5` 加 `sleep 5`，状态头 0.5 秒就对了，但 `run_bash` 实测 5.1 秒才返回——`subprocess.run` 超时只 kill 直接子进程，孙子进程还攥着继承的管道，收尾要等 EOF。既有行为，不是本次引入；按第 5 节 R6 的“处理子进程树”一并解决。
- **截断切尾会把 stderr 整段带走。** 触发：stdout 单独超过 40 万字符，报错落在被切掉的一侧，上下文和盘上那份都没有它（状态头还活着）。同样既有，处理方式是上文“补充限制”里那条流式落盘。

未做：7.2 人工验收里“执行无输出失败命令 → 模型可见非零退出码”这一行只验到工具返回值；工具结果到模型之间没有别的改写层（已核对 UI 与上下文层不解析这个格式），但没有跑真实模型端到端，该项继续标为未验证。

### R2：第二个实例可能误标第一个实例的任务

**位置：** [server.py](../server.py) 的启动入口，以及 [sessions.py](../sessions.py) 的 `reap_running()`。

当前先调用 `STORE.reap_running()`，再构造绑定端口的 `ThreadingHTTPServer`。`reap_running()` 会将所有 running 轮次改为失败。

**触发场景：** 第一个实例正在执行任务，用户再次直接运行 `server.py`。第二个实例可能先修改数据库，随后才因端口占用退出。`dev.py` 的启动检查不能覆盖直接启动入口。

**修复方案：** 以数据库路径为作用域取得进程级排他锁，成功后再初始化需要修改数据库的存储、执行恢复、开始接收请求。进程级锁必须在整个服务生命周期持有。模块级 `STORE` 初始化也需纳入启动顺序检查，避免第二实例取得锁前执行迁移。

仅把端口绑定提前可减少同端口冲突，但不能保证“同一个数据库只有一个写入服务”：不同端口仍可能共享同一数据库。建议明确支持单服务实例，暂不引入分布式锁或多进程调度。

**验收：** 使用临时数据库启动 A，并创建一个 running 任务；启动共享数据库的 B，B 必须拒绝启动，且 A 的状态不变。A 异常退出后，新的实例能取得锁并清理遗留任务。正常关闭也会释放锁。

### R3：保存失败后任务仍可能显示 completed

**位置：** [server.py](../server.py) 的 `_run_turn()`；[sessions.py](../sessions.py) 的 `finish_turn()`。

当前 `finish_turn()` 抛异常后只发送 note，后续 reply 仍使用 `outcome.status`。如果模型已完成，页面会收到 completed，但数据库事务可能没有提交，工作上下文仍是旧版本。

**触发场景：** 最终提交遇到数据库写入错误。用户看到完成后继续提问，模型可能读不到刚执行的结果。

**修复方案：** 区分“模型执行结果”和“保存结果”。保留模型已产出的文本，增加明确的保存失败信号。未提交成功不能发送普通的已持久化完成状态。如果数据库持续不可写，不得声称 failed 已经落库。

建议页面显示“执行已结束，但保存失败”，并允许复制结果。服务端记录该会话的保存故障，阻止其直接基于旧上下文开启下一轮，直到完成重新保存或用户明确选择恢复路径。不要为了补保存而重新调用模型或重新执行工具。

同时检查 `finish_turn()` 条件更新命中 0 行的情况：当前只打印日志，且上下文更新可能已经提交。建议将该状态冲突作为事务失败处理，在事务内验证并回滚，避免覆盖终态任务的工作上下文。

**验收：** 注入最终提交异常，页面必须出现保存失败且不显示普通完成；旧上下文不能被悄悄用于下一轮。恢复保存时工具执行次数不增加。条件更新命中 0 行时，上下文版本不变。

#### 实施记录（2026-09-22，R3）

**一句话：把"模型跑出什么"和"这一轮存没存上"分开。**

`sessions.py`：`finish_turn` 的条件更新命中 0 行从"打一行日志"改成**抛**
`TurnStateConflict`。不抛的话整个事务照常提交，而那一半上下文是按"它还在跑"算出来的 —— 提交上去就是拿旧账盖掉终态任务的工作上下文。抛出即回滚，上下文一个字不动。

`server.py`：`saved` / `save_error` 与 `outcome` 分开记；reply 事件的 `status` 在保存失败时发 `unsaved`（并另发 `model_status` / `saved` / `save_error`，"执行完了"和"存上了"是两件事）；没存上的那份进 `UNSAVED`，下一次问这个会话时**先补写再开新轮** —— `_flush_unsaved()` 只补写，**不重跑模型、不重跑工具**，补不上就回 503（不让旧上下文被悄悄用于下一轮）；`/turns` 补一个 `unsaved` 字段，刷新之后页面才知道那一轮不是"还在跑"。状态冲突不进这道闸：它重试也没用，进了这个会话就永远问不下去了。

`ui/index.html`：`STATE_TEXT` 加"未入库"、加一条 `data-status="unsaved"` 配色；新增 `saveFailureBox()`（红字 + 复制按钮：模型那段文字可能没进库，页面上是唯一一份）与 `copyBtn()`；直播 reply 与刷新两条路都接上。语法用 `node --check` 验过。

验收对照：

| 方案要求 | 落到哪 |
| --- | --- |
| 注入最终提交异常，页面不显示普通完成 | `test_保存失败_不显示成普通完成`；页面代码已落地（浏览器端人工验收未做） |
| 旧上下文不能被悄悄用于下一轮 | `test_保存失败之后_下一轮不许拿旧上下文偷偷开跑`（503，且一行轮次都不新增） |
| 恢复保存时工具执行次数不增加 | `test_库恢复之后补写_不重跑模型`（模型只被叫了两轮各一次，且第二轮历史里真有第一轮） |
| 条件更新命中 0 行时上下文版本不变 | `test_sessions.py::test_中途检查点与轮末收尾`（改成新语义：抛 + 版本号与"压过"的时间都不动） |
| 刷新之后页面还知道那一轮没存上 | `test_刷新之后页面还知道那一轮没存上`（`/turns` 的 `unsaved`） |

未做：**"用户明确选择恢复路径"**（放弃那份没存上的上下文、从库里已有那份继续）没有做 —— 现在只有"自动补写，补不上就 503"这一条路。要加得先想清楚 UI 上那个"放弃"点了之后用户会失去什么。

### R4：删除与执行之间存在竞态

**位置：** [server.py](../server.py) 的 `_post_delete()`、`_post_ask()` 与 `session_lock()`。

删除先调用 `is_running()`，再删除数据库记录。检查本身没有持有会话锁。可能出现“删除线程看到空闲 → 执行线程取得锁并开轮 → 删除线程删除会话”的交错。

**修复方案：** 删除和开始执行都取得同一个 sid 对应的锁；取得锁后再检查会话存在性。删除拿不到锁时返回冲突。将检查和操作放在同一互斥区间，保留现有锁对象不回收策略，避免同一 sid 出现两把锁。

**验收：** 用线程同步屏障确定性构造删除与执行竞争，不能依赖随机 sleep。执行先取得锁时删除返回冲突；删除先取得锁时后续执行发现会话不存在；不得出现已创建的任务因会话删除而写回失败。

#### 实施记录（2026-09-22，R2 + R4）

**R2 启动独占**：新增 `dblock.py` —— 按库路径取的进程级文件锁（Windows `msvcrt.locking`、POSIX `flock`，两者在**同进程内也互斥**，所以测试能在本地验它；换成 `fcntl.lockf` 会在同进程内假通过）。锁文件**永不删**：删掉一个别人正持着的锁文件，等于让下一个来的人在一把新锁上成功。

`server.py` 的模块级 `STORE = SessionStore()` 取消，改成 `open_store()`：`__main__` 里**先拿锁 → 再建库（含迁移）→ 再 `reap_running()` → 最后收请求**；拿不到锁直接退出，在这之前一个字节都不写库。会话库路径与端口可由 `AGENT_DB_PATH` / `AGENT_PORT` 顶掉 —— 进程级测试要起真服务，不能碰用户的库和 8765（§7.1 那条）。

**R4 删除互斥**：`_post_delete` 与 `_post_ask` 抢同一把 `session_lock(sid)`，并且**先拿锁再查存在性**。删除拿不到锁回 409；拿到锁之后才发现会话不在的回 404 —— 而不是一路走到 `begin_turn` 撞外键、回一句 500「cannot start turn」。

验收：`tests/test_startup_lock.py`（9 项：同进程/跨进程互斥、锁文件不删、强杀与正常退出都放锁、真起 A+B 验「B 拒绝启动且 A 那条 running 轮状态不变」、A 死后新实例接手并清理遗留轮）；`tests/test_session_delete.py`（5 项：用 Event 和脚本化的存在性回答卡死两条路径，不靠 sleep）。全套 225 项通过。

顺带：`config.py` 的 `MAX_ROUNDS` 从 50 改成 1000（不设人为上限，用来测长活能力）。代价写在那个常量上面了 —— 这一版没有钱和时间的闸，被忘掉的标签页能烧到 1000 轮，`ROUND_WARN` 仍是 3。

未做：R3 的**页面部分与验收用例**（服务端改动 `saved` / `UNSAVED` / `_flush_unsaved` / `TurnStateConflict` 已落地，但还没有测试，也没在页面上显形）；R5–R8 未开始。

### R5：多个会话可能覆盖共享文件修改

**位置：** [tools/edit.py](../tools/edit.py) 的 `run_edit()`、[tools/memory.py](../tools/memory.py) 的读改写路径。

会话可以并发运行，且共享 WORKDIR。两个调用都可能先读到同一个旧版本，再分别写回各自结果；后写入者覆盖前者修改，而两次调用都返回成功。记忆文件同样存在该问题。

**建议分层处理：**

1. 为应用自身的记忆读改写增加按规范化路径的锁，锁覆盖整个读取、校验、写入区间。
2. 文件编辑可以增加路径锁与版本校验；原子替换改善部分写入问题，但不能单独解决丢失更新。
3. 对当前共享目录的多会话执行，优先明确采用串行策略；如果需要真正并行改代码，再引入独立工作目录或 worktree。

Python 文件锁不会自动约束 bash、外部编辑器或另一个进程，因此不能承诺“加工具锁后所有写入都安全”。版本校验也需要结合明确的冲突处理策略。

**验收：** 两个并发记忆添加都保留，且容量检查在锁内完成。两个冲突编辑应串行处理或明确报冲突，不得都成功却丢失其中一次修改。测试仅使用临时文件。

### R6：缺少主动停止任务的完整机制

**位置：** [server.py](../server.py) 请求执行路径、[agent.py](../agent.py) 的循环与模型调用、[tools/bash.py](../tools/bash.py)、[tools/subagent.py](../tools/subagent.py)。

当前网页断开不等于取消，服务会继续执行。用户需要一个独立的停止动作。

**建议方案：** 每个活动 Turn 持有取消事件，由停止端点按 session 与 turn 精确定位。页面停止按钮触发该事件，主循环在请求模型前、模型返回后、每个工具开始前检查。重试退避与等待用户回答也必须可被取消唤醒。

执行中的模型流需要关闭或中断等待机制；仅在循环顶部检查不能实现及时停止。Shell 需要改成可控制进程生命周期的执行方式，并处理子进程树。子 Agent 继承父任务取消信号，不能父任务停了子任务继续执行。

新增 cancelled 终态前，需要迁移 SQLite 状态约束，并更新页面展示、历史重放和所有终态判断。可在请求取消后先显示“正在停止”，只有执行链确实停下并完成收尾后才显示“已停止”。

**历史一致性：** 如果模型一次返回多个 tool_use，而取消发生在其中一个执行后，应为未执行调用补充明确的取消结果，保持 tool_use/tool_result 配对。不要只留下半批结果。

**验收：** 覆盖模型等待、重试退避、Shell 执行、等待回答、两个工具之间、子 Agent 执行这六类时机。取消后不得启动下一项工具。重复停止幂等；停止已完成任务不改写终态；已完成的文件修改保留，并如实告知用户。

### R7：进程中断后模型上下文可能落后于文件状态

**位置：** [context.py](../context.py) 的 `prepare()`、[server.py](../server.py) 的 `_checkpoint()` 与 `_run_turn()`。

当前压缩改变消息后会保存检查点，轮末也会保存最终上下文；普通未触发压缩的完整工具回合没有同样的保存动作。突然退出时，历史展示记录可能已经存在，但后续模型加载的上下文仍停在旧版本或上次压缩检查点。

**修复方案：** 在完整 assistant/tool_result 批次结束后保存工作上下文。将普通执行检查点与压缩检查点区分，普通保存不得更新 `last_compacted_at`。检查点应能关联到 Turn 与批次或消息序号，以识别恢复位置。

启动时只处理遗留状态并展示中断信息，不自动重放工具。用户选择继续时，向模型提供最后可靠检查点和中断说明，要求先核实实际文件状态。

**不可消除的窗口：** 外部命令成功之后、工具结果保存之前仍可能崩溃。SQLite 提交无法与任意 Shell 副作用组成同一个事务，因此不能承诺恰好执行一次。检查点可以缩小丢失范围，不能让所有工具自动安全重试。

同一模型响应包含多个工具时，批次中途崩溃也会留下不确定操作。若后续需要更细恢复，应另行记录每次工具调用的开始与结果；不能仅把半批 messages 直接发回模型。

**验收：** 在完整批次保存后强制终止测试进程，重启后能加载该检查点。另测“工具已产生副作用但检查点未提交”，必须显示结果不确定，不自动再执行。保存后的消息保持调用与结果配对。

### R8：同步 README 与实现

README 仍有按字符上限描述压缩的内容，而实现已采用 token 估算预算；固定行数也会随着改动失效。

完成可靠性修改后统一更新：启动方式、独占实例约束、工具返回状态、取消语义、恢复限制、压缩预算说明。删除容易漂移的代码行数描述。

## 7. 验证策略

### 7.1 自动化测试

- 逻辑测试使用假的模型响应，不依赖网络、真实 API Key 或付费调用。
- 存储测试使用临时 SQLite 数据库，禁止用正在运行服务的真实会话库。
- 文件测试使用临时目录，禁止通过真实项目文件复现覆盖问题。
- 并发测试使用屏障或事件控制执行顺序，避免依赖概率触发。
- 进程测试使用专门启动的测试服务和测试子进程，不终止用户正在运行的服务。
- 数据库迁移测试同时检查旧数据保留、外键完整性与新增状态约束。

已有 `tests/conftest.py` 会隔离服务数据库和用量账本，新测试应保持这一约束。每批先执行相关测试，再在交付前执行完整测试集；测试数量可增加，不要求固定为 198。

### 7.2 人工验收

| 操作 | 期望表现 |
| --- | --- |
| 执行无输出失败命令 | 模型可见非零退出码（工具层已验（见 R1 节的实施记录）；真实模型端到端未做） |
| 活动任务期间重复启动服务 | 第二实例拒绝启动，原任务不受影响 |
| 模拟最终保存失败 | 页面保留回复并显示保存故障，后续执行不会静默用旧上下文（服务端与页面代码已验，浏览器端未做） |
| 执行期间删除会话 | 明确返回冲突，会话与任务记录仍完整 |
| 点击停止 | 先显示正在停止，收尾后显示已停止，不继续发起工具 |
| 刷新执行中的页面 | 能恢复展示与活动状态，不重复开启任务 |
| 进程中断后重启 | 显示中断与检查点信息，不自动重复有副作用的命令 |

## 8. 暂不扩大范围的事项

当前仍以本机、单服务进程使用为目标。本轮不要求引入任务队列、分布式调度、多用户鉴权平台或重写前端。

现有 Shell 黑名单不构成操作系统沙箱，这是已有实现的边界。若项目下一阶段变为处理不可信任务或向其他用户开放，应单独设计操作系统级隔离，不能靠增加关键词黑名单获得该能力。

压缩预算中的 token 估算是启发式方法。本次没有重新验证模型上下文容量或在线价格，不应据此修改预算或成本参数。可先增加输入估算与 API 实际用量的观测，再决定是否调整算法。

请求去重可作为后续增量：网络断开后重复提交有可能开启第二次执行；届时使用客户端请求标识和唯一约束返回既有 Turn，不能仅靠按钮禁用。但它不替代工具副作用的恢复设计。

## 9. 完成标准

下一阶段完成时，应能证明：失败命令不会被当成成功；重复启动不修改活动任务；保存故障明确可见；删除与执行互斥；共享写入策略清楚；取消能传播到实际执行；重启不自动重放不确定操作。

每项已修复问题都应对应可重复的验收测试。没有完成故障验证的项目继续标为待验证，不能因为普通流程正常或测试总数增加而视为解决。
