# Checkpoint v1：交给 AI 的实施说明

日期：2026-09-23  
状态：**已实施（v1，2026-09-23）**。正文仍是当时的实施规格，逐条对照见文末
「11. 实施结果」。  
目标仓库：custom-agent，包含当前工作区已有未提交修改

## 1. 给实施 AI 的任务

请为当前项目实现完整回合 checkpoint，以及服务重启后的显式续跑。先核对当前代码，再按本文分步修改并验证。保护工作区已有修改，使用独立临时数据库测试，不操作用户正在使用的会话库。

实现目标：用户的一次请求在多个工具回合之间被中断后，已经保存的有效上下文和运行进度可以恢复；发现检查点之外可能发生过操作时，阻止直接续跑并提供核对信息。

本轮用户尚未选择自动恢复方式，因此本文采用保守默认：**服务启动时只识别中断任务，由用户在页面点击“继续”；不自动重启任务。** 如果后续用户明确改变此选择，再调整入口行为，不能省略恢复检查。

所有下文标为“必须”的规则都是验收条件。建议的字段和函数名称可以按现有风格调整，但需要保持相同语义，并在交付说明里标明对应实现。

## 2. 范围和保证

### 2.1 本版包含

- 在完整工具回合结束、上下文压缩完成、必要控制消息变化后，保存有效工作上下文。
- 在接收请求时建立初始恢复点，在完成任务时原子保存最终上下文与终态。
- 持久化当前任务、已使用回合数、待办与恢复兼容性信息。
- 将恢复所依赖的原始消息记录改为严格写入，失败时停止推进执行。
- 启动后识别中断任务，区分可以续跑与需要核对的情况。
- 提供显式继续和放弃中断任务的入口，保留历史与不确定操作说明。
- 覆盖真实子进程被终止、重复恢复请求、写入失败等测试场景。

### 2.2 本版边界

- 恢复边界是完整工具回合，不恢复 Python 调用栈、半条模型输出或子 Agent 内部进度。
- 不自动执行检查点之后遗留的工具调用，不自动把尾部原始记录重建成新上下文。
  - **实施时这条边界往回挪了一点**：加了 `tool_execs`（两阶段标记）。它不是
    用来重放工具的，恰恰相反 —— 它存在的唯一目的是让"已经开始、结果未知"
    可判定，从而把**自动重放**的范围收得更紧（见 §11.2）。
- 不回滚已经发生的文件或外部系统修改，不承诺任意 Shell 操作恰好执行一次。
- 不恢复旧权限确认或旧提问的等待对象；存在这些未完成操作时进入待核对状态。
- 不同时实现任务取消、统一费用预算、完整工具执行表、多进程调度或恢复全部压缩档位。
- 本版主要处理服务进程被终止、正常重启等中断。当前 SQLite 使用 WAL 与 `synchronous=NORMAL`，系统断电后最新提交的持久性不等于进程退出恢复；不得据此宣称断电零损失或数据库与文件修改具有跨资源事务。

用户显式要求启动的后台进程或外部任务也不会因恢复上下文而自动停止；页面说明必须如实表达这一点。

## 3. 术语与现有代码定位

| 术语 | 含义 |
| --- | --- |
| turn | 用户的一次请求，复用现有 `turns.id` 和 `turn_no` |
| round | 一次主循环模型调用及其整批工具处理 |
| checkpoint | 已持久化、允许作为恢复基础的完整工作状态 |
| 覆盖水位 | checkpoint 已处理到该 turn 的哪个 `message_no`；不等同于全库消息行号 |

| 待核对 | 存在未纳入 checkpoint 的记录，v1 不判断它们可以安全重放 |

### 当前已确认的事实

1. `session_contexts` 已保存 `messages_json`、版本和压缩时间，每个会话一份。
2. `prepare()` 当前只在确实压缩时调用 checkpoint；普通工具回合末尾只追加 `messages`。
3. `turn_messages` 逐条保存原始消息，工具结果落库后才在工作上下文里加上 `m...` 编号。
4. `append_turn_message()` 写入失败会返回 `None`；当前恢复要求需要改变主 Agent 的这条处理路径。
5. `_checkpoint()` 失败后目前只发提示；`_run_turn()` 的 `finally` 仍尝试保存内存中的最终上下文。
6. `make_recorder()` 的计数从 2 开始，`rounds` 与待办目前主要存在内存中。
7. 启动清理把遗留 `running` 标为 `failed`；`turns.status` 的 CHECK 只允许三种状态。

## 4. 不可破坏的约束

1. **配对完整。** 只有全部 `tool_use` 获得对应 `tool_result` 后，才把这一批纳入 checkpoint；编号已经添加，待办提醒也已并入消息。
2. **原文可追溯。** 保存实际有效的 `messages`，保留压缩摘要、消息编号和协议需要的内容块。原始消息继续追加存储，不能从截断后的 `events` 重建。
3. **写入先于副作用。** 完整 assistant 响应必须严格落库成功后，才能执行其中任何一个工具或进入工具前置 hook。写失败时工具调用次数必须为零。
4. **结果写入先于下一步。** 工具已返回但结果写入失败时，不执行后续工具，不请求模型；保留最后一个已提交 checkpoint。
5. **持久化原子。** 快照正文、归属、覆盖水位、版本和运行快照同一事务提交；失败不得只更新一部分。
6. **完整上下文整体替换。** 压缩会改写列表结构，不能通过旧列表下标向数据库增量拼接；保留调用方列表引用需要的切片赋值语义。
7. **互斥和归属。** 执行、继续、放弃、删除都使用同一会话锁；每次写入确认 turn 属于该 session，状态和版本仍符合预期。
8. **展示故障不决定执行状态。** 页面断流可以按原有方式处理；恢复关键数据写入失败必须传播。不要把两种错误都交给 `quiet()` 吞掉。
9. **不扩大权限。** 点击继续只表示继续该任务，不能复用此前尚未完成的权限确认，也不能默认允许任何越界操作。

## 5. 数据模型建议

第一版沿用“每个会话一份最新有效快照”。有未解决的中断任务时阻止开启新 turn，避免新任务覆盖唯一恢复点。历史浏览和删除仍可按既有权限及互斥规则处理。

### 5.1 扩展 `session_contexts`

| 字段 | 语义 |
| --- | --- |
| 已有 `messages_json` | 当前完整工作上下文 |
| 已有 `version` | 每次成功保存递增，恢复请求据此检查快照是否过期 |
| 已有 `last_compacted_at` | 只有实际压缩时更新；普通 checkpoint 不更新 |
| `checkpoint_turn_id` | 快照所属 turn；旧数据可以为空 |
| `covered_message_no` | 该 turn 中已经纳入处理的原始消息水位 |
| `runtime_json` | 带独立格式版本的运行状态，见下文 |

`runtime_json` 至少包含：已完成 round 数、`rounds_since_todo`、待办条目、原始任务的引用或原文，以及原始模型、实际 system prompt、原始 `max_rounds` 和恢复兼容性签名。不要保存客户端实例、锁、线程、回调、凭据或任何 Python 对象序列化。

恢复兼容性签名至少覆盖工作目录、工具 schema、恢复协议版本和相关执行代码版本。不能仅用 Git HEAD 代表有未提交修改的代码，可采用相关源文件内容指纹。发现不兼容时禁止静默换模型、提示词或工具继续；展示原因。

### 5.2 扩展 `turns`

- 增加 `interrupted` 状态，与正常模型或工具错误产生的 `failed` 区分。
- 增加机器可读的中断原因，区分进程中断、关键记录保存失败、checkpoint 保存失败等。
- 持久化 `model_rounds_started`，表示已经发起或预留的主循环逻辑调用次数。

发出主循环模型请求前，在短事务中检查原始回合上限并递增 `model_rounds_started`。这个计数必须独立于可能较旧的上下文快照更新，恢复时不能回退。预留成功后崩溃，即使请求尚未实际发出，也保守计入已使用次数。SDK／`call_api` 内部重试仍沿用现有口径，费用继续由账本记录；本版不重定义主／子 Agent 的预算体系。

### 5.3 迁移要求

- 添加新迁移，不修改已应用迁移的正文；实际迁移版本以实施时仓库为准。
- 修改 `turns.status` CHECK 需要处理 SQLite 表重建，必须保留关联表数据、外键、唯一约束和索引。
- 遵守现有事务迁移约定，不用会隐式提交的方式破坏原子性；通过 `foreign_key_check` 和迁移失败回滚测试。
- 旧版上下文缺少新元数据时仍能正常浏览和开始普通新任务；旧版遗留任务标为不可直接续跑，不伪造恢复信息。
- 不在用户正在运行的数据库上试验迁移。

## 6. 保存流程

### 6.1 开始新 turn

拿到会话锁后，检查没有未解决的中断任务，读取已有上下文及记忆快照，构造当前用户输入、system 和运行初态。在同一事务中创建 turn、记录用户输入并保存初始 checkpoint。事务成功后才发起模型调用。

初始 `covered_message_no` 通常为用户输入的序号。确认初始保存没有重复追加用户文本；现有 `_run_turn()` 中的追加位置需要一起调整。

### 6.2 每个工具 round

```text
检查并持久化本次模型调用的回合计数
  → 调用模型
  → 严格保存完整 assistant 响应
  → 按顺序处理每个工具
      → 权限与 hook
      → 执行 handler 或得到拒绝结果
      → 严格保存结果，取得原始消息行号
      → 给工作副本添加消息编号
  → 全部结果和待办提醒追加到 messages
  → 验证工具调用与结果完整配对
  → 同步保存 checkpoint
  → 才能进入下一次模型请求
```

当前回合只有部分工具执行完时，保留逐条原始记录，但不覆盖完整 checkpoint。权限拒绝是一个已知工具结果，可以按正常结果加入完整回合；权限等待被进程中断则属于未完成尾部。

### 6.3 压缩与控制消息

- 自动压缩处理完完整上下文后保存，准确更新 `last_compacted_at`。本次不启用当前已关闭的压缩档位。
- 模型主动调用 `compress` 会在工具执行中修改工作列表；要等该批工具结果全部回填后统一保存，不能在 handler 内保存半个回合。
- `Stop` hook 添加继续工作的控制消息等情况，也必须在下一次模型请求前保存相应有效状态。
- 临时附加到 API payload 的回合上限提醒可以按恢复后的计数重建，不把展示日志当作唯一依据。
- 将“是否有语义变化”和“是否确实压缩”分别表达。可让 `prepare()` 返回变更信息或回调 loop；保存的所有权由 loop／server 统一管理。
- 每次完整回合同步保存；第一版不改成定时、后台或只在超预算时保存。连续边界无变化时可以去重，但不能为了减少写入而漏掉水位或运行状态变化。

### 6.4 正常结束

继续沿用最终上下文与 turn 终态同事务提交的规则。更新 checkpoint 元数据，终态任务不可通过恢复入口再次执行。正常失败、输出截断与回合上限等现有语义必须保持明确。

## 7. 写入失败的处理

为主 Agent 增加严格记录接口，或在现有接口增加明确的严格模式。展示事件仍可尽力写入；恢复关键的 assistant、tool result 和控制记录必须失败可见。

定义可识别的持久化错误类型，在业务工具的一般异常转换之外传播。尤其要防止 `agent_loop` 中的 `except Exception` 把保存失败变成普通工具错误，然后继续运行。

发生严格记录或 checkpoint 保存失败时：

1. 停止推进模型、工具和子 Agent，不对工具做自动重试。
2. 保留最后一个已经提交的 checkpoint；允许有限次数重试同一份数据库写入，不能重新执行模型或工具来“补结果”。
3. 数据库仍可写时，将 turn 单独标为 `interrupted` 并记录原因；状态更新不能覆盖 checkpoint。数据库完全不可写时，向当前页面说明失败，后续启动再处理遗留 `running`。
4. 调整 `_run_turn()` 的 `finally`：不能经普通 `finish_turn()` 把这时内存中的未检查上下文覆盖到最后可靠快照。
5. 明确 `_flush_unsaved()` 的适用范围。保留正常最终保存失败的补写行为，但不能让旧补写路径把 checkpoint 故障任务静默变成可继续。

返回“结果已经生成，但保存失败”时，要同时说明哪些内容仍未持久化。不能显示普通成功，也不能声称已经撤销操作。

## 8. 重启与恢复判定

### 8.1 启动

保持现有顺序：先取得数据库独占锁，再打开和迁移数据库，再处理遗留任务。将本进程接手的遗留 `running` 标记为 `interrupted`，只做识别，不启动模型或工具。

### 8.2 可以续跑的必要条件

以下条件全部满足，才提供可执行的“继续”：

- turn 是当前会话未解决的中断任务，且没有后续新 turn。
- checkpoint 归属、格式和消息配对有效，运行元数据齐全。
- 所引用的原始消息、转录或工具输出产物仍可用；缺失时给出原因。
- 模型、system、工具与执行代码满足兼容性要求，工作目录一致。
- 同一 turn 不存在 `message_no > covered_message_no` 的尾部原始消息。
- 已预留的模型回合数没有耗尽原始上限。

本版对尾部采用保守规则：**只要有尾部原始消息，就不直接续跑。** 包括已保存但尚未 checkpoint 的完整响应、部分或全部工具结果，以及未完成的提问记录。即使其中某些情况可以人工证明安全，v1 也不自动重建或重放。

这条规则成立的前提是 assistant 响应严格落库成功后才允许任何工具执行。若模型请求期间崩溃、没有产生严格记录，则可从最后 checkpoint 再发起一次模型请求；之前预留的回合数仍然保留，且不承诺前一次请求未计费。

**已有尾部可以从数据库查出；关键记录失败也可能只留下旧状态。因此不能把“没有尾部”当作唯一条件，必须同时处理机器可读的中断原因、最后可靠进度以及上述执行顺序约束。** 对无法解释的状态默认进入待核对。

### 8.3 显式继续

建议增加 `POST /session/{sid}/turn/{tid}/resume`，请求携带 `expected_checkpoint_version`。

在会话锁内重新验证全部条件，不能信任页面先前显示的可恢复状态。在事务中核对版本，将同一个 turn 从 `interrupted` 转为 `running`，清理对应终态时间并记录此次恢复。恢复控制记录若进入原始消息表，应与更新覆盖水位及快照版本同事务提交，避免它自身形成未处理尾部。

然后恢复实际 `messages`、原始任务、原始执行配置、待办和循环计数，重新绑定当前请求的 emit、ask 和 recall。`make_recorder()` 从数据库中的最大 `message_no + 1` 继续，不能重置为 2；工具结果的 `m...` 编号仍使用原始消息主键，不重新编号。

续跑不调用 `begin_turn()`，不新增用户任务，不把“继续”当成新的用户问题追加进去。既有 `turn_id`、`turn_no` 和用量归属保持不变。已有回合预算不足时返回明确原因，不因为重启恢复额度。

两个并发恢复请求只能有一个进入执行；另一个得到冲突。对 running、completed、普通 failed、过期版本或错误归属的恢复请求，拒绝且不产生模型／工具调用。

### 8.4 待核对和放弃

页面展示最后 checkpoint 时间、已完成回合数、中断原因，以及尾部记录中的工具名称、参数与已知结果。明确区分“模型请求执行”“有结果记录”“结果未知”，不能把有 `tool_use` 一概说成已执行，也不能把无结果说成未执行。

v1 提供查看详情和放弃本次中断任务，不提供“强制从旧 checkpoint 重放”。核对后自动归并尾部、逐个恢复未执行工具等属于后续版本。

可增加仅适用于 interrupted 状态的放弃入口，同样带版本并取得会话锁。显式放弃时保留原始记录，将任务转为带原因的 failed，并把“用户已结束本次中断任务；哪些操作结果仍不确定”的恢复说明加入后续有效上下文，再允许新 turn。相关状态、说明和快照更新同事务提交。说明应引用原始记录，工具内容仍作为不可信参考资料处理。

放弃只结束恢复流程，不回滚文件、不清理未知外部操作，也不等同于取消仍在运行的任务。

## 9. 实施顺序与交付检查

每一步完成后运行适当测试，再进入下一步。以下步骤共同构成 v1，不能只在 round 末尾加一次 `save_context()` 就宣称完成恢复能力。

1. **数据与迁移**：扩展状态、进度和 checkpoint 元数据；实现原子保存、回合预留、归属与版本检查。
2. **严格记录与错误传播**：保证调用前记录成功、结果写失败后停止；调整最终收尾和旧补写路径。
3. **主循环保存边界**：初始、完整工具批次、压缩、控制消息与最终保存；覆盖主动 `compress`。
4. **恢复状态**：恢复原始任务、待办、计数、配置、消息编号；兼容无持久化回调的子 Agent。
5. **启动与接口**：中断识别、可恢复性查询、显式继续、放弃；维护会话互斥和重复请求保护。
6. **页面与验收**：显示中断和待核对状态，完成端到端故障测试，更新 README 与生产化文档状态。

### 11.2 三处与规格不同，都是往保守一侧挪

1. **`tool_execs`（规格里说 v1 不做的那张表）做了。** 理由在实施中变得很具体：
   §8.2 用"水位之后有没有原始消息"判尾部，而一条崩在 handler 里的工具**没有**
   对应的原始消息 —— 它只有那条 started 标记。不做这张表的话，那种情况会被判成
   "可以续跑"，然后模型把一条已经动过机器的命令再跑一遍。这是 §4.1/§4.4 想要的
   东西的反面，所以补上了。
2. **没有为 `expected_checkpoint_version` 单独建字段**：`session_contexts.version`
   本来就是这个语义（每存一次 +1），比它更准。
3. **`interrupt_reason` 只写机器读的短码**（`process_restart` / `persist_failed`），
   人话放在 `error_message`。页面按短码决定画哪些按钮，不拿中文句子做匹配。

### 11.3 已知的边界（v1 就这样）

- **放弃之后不能反悔**：那一轮收成 `failed`，快照被那段说明覆盖。没有"退回放弃前"。
- **尾部记录不自动归并**：水位之后只要还有东西，续跑入口一律拒绝，只能放弃。
  自动核对、逐条恢复未执行工具是后续版本。
- **不做跨资源事务**：文件改过的、命令跑过的，都不回滚；外部进程不因恢复而停止。
- **`sessions.db` 的 WAL + `synchronous=NORMAL` 没变**：断电的持久性保证不在这一版
  范围内，恢复针对的是进程被杀与正常重启。
